## 지금 위치

- 완성도: **1단계** — 내 컴퓨터에서만 돈다. DB, Ollama, 백엔드, AI 서버, USB 연결, 앱을 손으로 차례로 켜야 한다.
- 목표 단계: 4단계 + 5단계 일부 (③)
- 끝나는 날: 2026-12-31 목표. 늦어지면 주간 점검에서 범위를 줄이거나, 이유를 적고 날짜를 옮긴다.

완성도 6단계: 1 내 컴퓨터에서 돈다 → 2 남이 받아서 돌린다(README, docker compose, `.env.example`) → 3 배포 → 4 실제 사용자가 쓰고 의견을 받아 고침 → 5 혼자 굴러간다(CI, 오류 기록, 백업, 다시 배포하는 방법) → 6 제품(인증, 개인정보, 법적 검토, 확장)

## ② 누가, 무슨 문제

- 누가: 30~50대, 영양제를 챙겨 먹기 시작하는 세대
- 무슨 문제: 아파서 약을 받아왔을 때 이런 게 궁금하다.
  1. 내가 먹는 약이 뭔지 (약 검색 — 기본 기능)
  2. 기존에 먹던 영양제를 계속 먹어도 되는지 (약 × 영양제 비교)
  3. 약을 먹는 동안 내 증상에 좋은 영양제가 무엇인지 (영양제 추천)

## ③ 목표 단계와 범위

- 목표 단계: **4단계 + 5단계 일부**(CI, 오류 기록, 백업) (2026-11-25)

| 하는 것 | 안 하는 것 (이유) | 나중에 |
|---|---|---|
| 세 기능(약 검색, 약 × 영양제 비교, 영양제 추천) 배포 | 아이폰 — 다른 사람 폰에 설치하려면 유료 개발자 계정이 필요하고 절차가 복잡하다 (2026-11-24) | (아직 없음) |
| 로그인, 약·영양제 목록을 계정에 저장 | 정식 출시 — 출시하면 의료 서비스 관련 문제가 생길 수 있다 (2026-11-25). ①의 첫 줄 표현도 이 전제로 그대로 둔다 | |
| 영양제 추천 개선 (확인 중) | | |
| 지인 약 10명 사용, 의견 반영 | | |
| CI, 오류 기록, 백업 | | |

결정 메모:

- **로그인을 넣는다** (2026-11-25). 제대로 된 서비스로 보이려면 필요하다. 3월의 "로그인 범위 제외"(2026-03-28)를 바꾼다. 목록을 계정에 저장하면 건강 정보를 서버에 두게 되므로 비밀번호 암호화 저장, HTTPS, 무엇을 저장하는지 안내, 탈퇴하면 지우기가 함께 필요하다.
- **영양제 추천은 핵심 기능이다** (2026-11-25). 지금은 추천이 잘하는지 잴 방법이 없다(①에도 추천을 재는 줄이 없음).

## ④ 가장 모르는 것

| 모르는 것 | 후보 | 확인 방법 | 결과 |
|---|---|---|---|
| 영양제 추천을 어떻게 만들지 | A. 비용을 감수하고 좋은 모델(API) 사용 / B. 복용 중인 약의 데이터에서 결과를 뽑아냄 / C. 증상에 좋은 영양소는 식약처 건강기능식품 기능성 원료 자료에서 찾고, 약과 부딪히는지는 지금 있는 비교 기능으로 거름(자료가 쓸 수 있는 형태인지 먼저 확인) | 추천이 잘했는지 재는 시험을 먼저 만들고, 같은 시험으로 후보를 비교 | (고민 중) |
| GPU가 필요한 모델(사진 인식, gemma)을 어디서 돌릴지 | (정리 전) | 지금 모델과 비교 중인 후보 모델 둘 다로 비용·속도·동시 사용을 시험 | |

- 추천은 원래 최신 LLM에 복용 약과 증상을 넣어 필요한 영양소를 받는 방식이었다. 로컬 모델로 바꾸면서 이 방식이 불가능해졌다(2026-11-25).

## ⑥ 작업 규칙

2026-11-25 확정.

1. **작업 단위:** GitHub Issue 하나 = 작업 하나, 하루~이틀 크기. Issue에는 왜 하는지와 끝났다고 볼 조건을 적는다. Issue는 사용자가 직접 만든다.
2. **진행 순서:** 무엇을·왜 하는지 먼저 설명 → 동의 → 구현 → 보고(어떻게 했는지 / 결과 / 다음 할 일) → 사용자가 자기 말로 설명하면 끝.
3. **완료 기준:** 동작 확인 + 테스트(자동 테스트, 화면은 직접 확인한 결과) + 배포 반영(배포가 생긴 뒤부터) + 기록(결정이나 문제 해결이 있었을 때).
4. **커밋·PR:** develop에 커밋 → 사용자가 push → Issue 하나가 끝날 때마다 PR로 master에 합친다. PR 설명은 무엇·왜·어떻게 확인했나 + `closes #번호`.
5. **모델 원칙:** 모델 약점을 코드 규칙으로 메우지 않는다. 부족하면 같은 시험으로 다른 모델과 비교한다.
6. **세션:** 계획·주간 점검은 계획 세션, 구현은 개발 세션.
